## Pasos y verificación

`tests/e2e/csv-import.spec.ts` y las fixtures CSV del piloto son entregables por crear; no forman parte de la base analizada.

1. **Levantar un entorno reproducible y local al job.** Añadir configuración y script de pruebas para una instancia Supabase efímera con Auth y correo capturado localmente. Fijar CLI e imágenes compatibles; no existe `supabase/config.toml` versionado en la base analizada. Aplicar migraciones versionadas, cargar `supabase/seed_demo.sql` según su contrato y crear usuarios sintéticos con portafolios vacíos separados de la demo. Usar fixtures de precio/FX y desactivar integraciones externas en CI mediante configuración de test; no modificar el esquema ni el comportamiento de producción. Comprobar que los endpoints y las credenciales provienen solo del stack efímero; no usar claves reales, respaldos ni proveedores de mercado. No añadir endpoints de siembra o bypass de login a la app. **Verificar:** `supabase` local queda listo, demo y API autenticada devuelven datos fixture, no hay acceso a servicios reales. Registrar IDs, procesos y cierre. Si las migraciones actuales no se pueden aplicar limpiamente, detener y reportar la migración y el error; no omitirla ni usar producción como salida.
2. **Probar el build servido, no el servidor de desarrollo.** Entrar con `pnpm install --frozen-lockfile`, `node init.mjs`, `pnpm lint`, `pnpm typecheck`, `pnpm test:run`, `pnpm build`. En CI, usar la versión de pnpm del manifiesto y fijar Node compatible con ella (Node 24 es la referencia del arnés); `NEXT_PUBLIC_*` y URL del sitio se fijan antes del build para el entorno de prueba. Instalar el navegador con `pnpm exec playwright install --with-deps chromium`. En `tests/e2e/home.spec.ts`, comprobar `/` permanece pública y muestra `demo-banner`; `/trades` sin sesión va a `/login` y la ruta API privada devuelve `401`. Conservar aserciones de formulario de correo. En `tests/e2e/csv-import.spec.ts`, iniciar sesión con flujo real y correo local; subir fixture sintético determinista, confirmar y verificar por API autenticada una sola operación persistida y el importe invertido exacto para esa fixture, usando el agregado vigente (`/api/v1/dashboard/aggregate`) y el contrato propio de cada campo. Reconfirmar el mismo `import_id`: `409`, mismo número de operaciones, mismo importe. Comparar con monto esperado calculado independientemente, no contra el primer resultado solamente. **Verificar:** `pnpm test:e2e -- tests/e2e/home.spec.ts tests/e2e/csv-import.spec.ts` ejecuta todos los casos requeridos y devuelve 0. No usar un skip de entorno para convertir un fallo en verde ni habilitar el test de precios históricos como parte de este cambio.
3. **Integrar sin duplicar build ni ocultar resultados.** Añadir a `.github/workflows/ci.yml` un job o pasos del E2E que consuman el build del mismo commit y su ambiente correspondiente. Dar `contents: read` a CI, tiempos límite y reportes de fallos; no publicar cookies, almacenamiento de Playwright ni trazas autenticadas sin sanear. Mantener lint/tipos/unitarias independientes del resultado del E2E, presentar un check funcional estable que no pase si un job obligatorio se omite. **Verificar:** `git diff --check`, `actionlint .github/workflows/ci.yml`, comandos del paso 2. Después, con permiso para publicar, demostrar rojo → bloqueo de merge → verde en un PR de prueba. Ejemplo inocuo: cambiar temporalmente el importe esperado en la misma prueba y confirmar que la aserción falla en el check de CI.
4. **Ensayar la entrega fuera de producción.** Vercel Hobby y Supabase Free son la restricción documentada. Confirmar con el propietario qué integración, rama, plan y destino están habilitados. No agregar infraestructura paga. Usar una sola autoridad de publicación; con permisos explícitos, desplegar el candidato identificado por SHA, registrar ID e inspeccionar portada/demo y ruta privada. Promover exactamente el candidato si el proveedor lo permite; si reconstruye, comprobar SHA y repetir smoke sobre el despliegue resultante. Ensayar publicar una revisión de prueba y recuperar la última sana, verificar SHA y smoke después de recuperar. Si un cambio tiene migraciones, comprobar compatibilidad con la versión anterior o exigir plan de datos y respaldo antes de promover. **Verificar:** evidencia de versión, resultado del smoke, restauración y tiempo medido. Si el plan del proveedor no permite un destino aislado u aprobación segura, dejar producción manual y anotar la limitación; no aceptar un autodeploy que ignore CI.
